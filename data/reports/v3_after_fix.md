# v1.0 修复后重跑（2026-11-06）

> 目的：验证 4 个 P1 修复 + 2 个口径修正后的真实结果，不把“指标口径变了”误写成“模型变好了”。

## 1. 本次改了什么

- `is_refusal`：不再用 `REFUSAL[:6] in t`；正常回答里出现“根据现有资料”不再误判拒答。
- 数字核验：按 `(数值, 规范单位)` 比对；`5年` 不再被 `5%` / `5人` 蒙混过关；无引用回退标记 `low_confidence`，主指标只算 cited。
- `cited_doc_ids`：改为复用 `check_grounding` 的出处匹配，不再用文件名前 12 字符；`doc_equivalence` 也应用到 cited docs。
- multi 保底：`final_ids[-1] = must` 改为替换非 must 槽位，多个子问题的头部块不会互相覆盖。
- `mean_latency_ms`：分母改为全部记录，不再用“全量耗时 / scored 数”。
- 默认评测口径：`Config.eval_gold` / `judge_l1.py` 默认切到 v3 73 条。
- `verify.py`：68 → 77 项，补了拒答误判、数字单位、引用 doc 匹配、multi 保底、v3 默认口径等回归项。

## 5. 必须保留的负面结论

1. **Recall@5=1.000 不可复现**。同一套 73 条、同一 v2 prompt，重跑得到 0.9559；旧 1.000 是单次天花板，不能继续当作稳定能力宣传。
2. **下降集中在 3 条查询，不是 4 个 P1 修复造成的**：
   - “公司给员工做完培训后……”：旧 run 拆 1 个子问题，新 run 拆 3 个；子问题检索把原问题直接命中的文件挤掉了。
   - “深圳毕业5年内……初创企业补贴和场租补贴”：拆成两个子问题后，2023 年稳就业通知没有进入 top-5。
   - “2010年养老金重新计算”：诊断时新旧保底逻辑都能命中，正式 run 没命中，属于查询分析/检索方差。
3. **multi L1 下降 10.5pp** 与上述 2 条 multi 召回丢失一致；不是 `ensure_sub_question_coverage` 的回归（诊断中新旧保底逻辑结果相同）。
4. **引用精度上升不等于引用正确率上升**：它主要来自“不再用 12 字前缀把一堆人社局文件都算成引用”，是口径修正。
5. **P95 仍接近 50 秒**：延迟的小幅下降不能说明交互体验达标。

## 6. 下一步（按优先级）

1. **保留原问题直检结果**：`_retrieve_multi` 在子问题 RRF 之外，增加原问题 top-1/top-2 作为候选或 must，避免子问题把原问题直接命中的文件挤掉。
2. **只对真正的 multi 题启用子问题路径**：当前 fact 题只要被拆出 3 个子问题也会走 `_retrieve_multi`，这次就损失了 1 条 fact。
3. **独立 holdout**：这次 1.000 → 0.9559 已经说明单次评测不够；需要 30 条冻结后只跑一次的 blind set。
4. **clause-level gold**：当前 Recall 仍是文档级，不能说明“检索到正确条款”。
