## 0. 两条链路

**离线：建索引**

```text
data/raw/*.md（458 份）
  → ingest/loader.py          拆 front matter + 清洗正文
  → ingest/clause_splitter.py 多级编号切分 → 条款块 → 二次切分/碎片合并
  → ingest/metadata.py        组装元数据 → data/chunks.jsonl（4583 块）
  → index/embedder.py         BGE 编码（CPU）
  → index/store_faiss.py      FAISS 索引 → F:\refrag-data\index
  → retrieve/hybrid.py        同时构建 BM25 内存索引
```

**在线：同步 ask()**

```text
问题
  → generate/query_analysis.py  LLM 抽 city/year + 拆子问题（失败退回规则版）
  → retrieve/hybrid.py          向量 top-20 + BM25 top-20
  → retrieve/fusion.py          RRF 融合
  → retrieve/filter.py          元数据过滤（city / year_gte / year_lte）
  → (multi 可选) retrieve/doc_select.py
  → retrieve/rerank.py          Cross-Encoder 精排 → top-5
  → generate/generator.py       DeepSeek 生成 → 回答 + 出处 + 时效提示
  → generate/verify.py          生成后核验引用真实性 + 数字溯源
  → app/pipeline.py             组装返回
```

**在线：流式 ask_stream()**

```text
ask_stream()
  → 复用 _retrieve()：查询改写/分析/混合检索
  → stream_answer()：llm.stream() 逐 token 输出
  → 流结束后 check_grounding()
  → UI：st.status 显示检索阶段 → st.write_stream 输出 → 核验徽章最后出现
```

`ask()` 保持同步，CLI 和评测继续使用；流式只新增入口，不替换同步路径。

## 2. 关键设计

1. **条款切分优先于固定长度**：政策语义单元就是条款；检索到半条等于拿到半条规则。
2. **多级编号识别**：458 份里只有 234 份（51%）含「第X条」；其余是 `（一）` / `1．` / `一、` / `（1）`。
3. **混合检索 + RRF**：向量不懂字面量，BM25 不懂同义改写；RRF 只依赖排名，避免分数量纲问题。
4. **粗排 + Cross-Encoder 精排**：精排提高相关性，但 CPU 代价高，是端到端延迟的主要来源之一。
5. **生成后规则核验**：不信任模型自己写的出处；引用映射回本轮 chunk，数字回溯原文。
6. **时效提示由规则层兜底**：只看文件年份和标题废止词，只说“可能过期”，不假装知道真实失效状态。
7. **P0 关思考**：`reasoning_effort=none` 只改生成客户端；A/B 证明延迟显著下降，但数字/stale 质量有回退，所以产品默认仍是 default。
8. **P2 流式**：`ask_stream()` 返回 token 迭代器，sink 保存最终 citations/refused/usage；核验必须等流结束。
9. **P3 口径**：纯规则查询分析只作为新增对照列；旧报告数字不改；同集重跑存在 LLM 查询分析噪声。

## 5. 已知边界

1. **没有 blind holdout**：73 条是固定 gold，所有数字都是同集重跑。
2. **默认口径不是 1.000**：v1.0 的 1.000 是旧口径；v1.1 为 0.9853；当前 default A/B 单次复跑为 0.9559，受查询分析和生成波动影响。
3. **stale L1 仍是 0.7442**：缺政策生命周期元数据，规则层只能提示风险。
4. **端到端首字仍约 6.8s**：生成阶段首字 <1s，但检索/精排约 4.9s；P2 没有改检索。
5. **clause gold 仅 24 条**：不能代表 multi/stale；16 条 evidence 是自动摘录。

## 6. 常见问题

| 问题 | 回答要点 |
|---|---|
| 怎么保证切分没切坏？ | `verify.py` 断言块数、clause_path、条款粒度、无重复；当前 93 项 PASS，4583 块 |
| 为什么 BM25 用 jieba？ | 中文无空格；jieba 分词后才能算词频，装不上时退化为字符二元组 |
| 元数据过滤为什么在内存做？ | 4583 块规模内存过滤足够快；换向量库时应下推成标量过滤 |
| 引用准确率怎么算？ | 正则抽 `[出处: 文件名（条款号）]`；文件级/条款级映射回本轮 chunk，数字再回溯原文 |
| 流式会不会重复检索？ | 不会；`ask_stream()` 只调用一次 `_retrieve()`，之后只流式生成和核验 |
| 为什么核验不边流边做？ | 引用和数字必须等全文结束才能稳定解析；先流完，再核验，再显示徽章 |
| TTFT 到底多少？ | 生成首字 P50 715.55ms；端到端首字 P50 6780.16ms，两者不能混写 |
| 小样本怎么敢下结论？ | 不敢；用 bootstrap 区间和配对检验，报告里直接写“不显著” |
